# rpatch v0.4.1 の試用メモ

2026-10-01、`~/project/prod/beat-jam` のセッション（Claude Code、Opus）で、普段の作業の中で使いながら気づいたことを追記していく。`rpatch -V` で 0.4.1。

## 使った場面

1. 3 ファイルに 1 か所ずつ、区切り形式・`--diff` つき（docs の参照の修正、Markdown の表に 1 行足す、テンプレートの 1 行の書き換え）。1 回で通った。
2. 計画の文書の、長い 1 行の前に 1 行を挿入。区切り形式で行の先頭だけを OLD に書いて止まり、JSON（行の途中でも照合する）に切り替えて通った。
3. JS の関数の中の 8 行を、FROM / TO で 12 行に置き換え（`--diff`）。FROM に 1 行目、TO に次のブロックの先頭 1 行だけを書けばよく、間の 6 行を写さずに済んだ。1 回で通った。
4. HTML の中の JS の関数（テンプレートリテラルに `${…}` とバッククォートが入れ子）を、区切り形式で 5 行 → 13 行に書き換え。1 回で通った。
5. 2 ファイル（.mjs と .html）に 1 行ずつ、1 回の呼び出しで。どちらも長い 1 行（200 文字超）だったが、行全体を写して通った。
6. シェルスクリプトの `case … esac` の後ろに 10 行を足す（OLD に末尾 2 行、NEW に同じ 2 行 + 足す行）。1 回で通った。
7. JSON で 1 ファイルに 2 か所（長い 1 行の末尾に文を足す、行の後ろに 1 行を足す）。どちらも行の一部を `old` にした。
8. 対象のファイルが別のリポジトリ（絶対パス）。問題なし。
9. このメモ自体の追記で、場面 2 と同じ間違い（長い 1 行の先頭だけを OLD に書く）をもう一度した。3 つの編集のうち 3 つ目だけが外れ、何も書き込まれなかった（全部か無しか）。

## 良かった点

- **行の一部だけを書いたときの診断**（場面 2）: 「found only as part of a line」と、見つかった行番号・行の全文・「行全体を写すか JSON を使う」のヒントが出て、何をすればいいかすぐ分かった。v0.2.0 の「空白違い」と出る件は直っている。
- `--diff` の出力が、ファイルごとの `M <file> edits=1 at_lines=…` のあとにまとまって出るので、3 ファイルの変更を 1 回で確かめられた。
- 日本語・バッククォート・`{{…}}` を含む行を、エスケープなしでそのまま書けた。
- **FROM / TO がいちばん効いた**（場面 3）。関数の中身を丸ごと書き換えるとき、Edit ツールや python だと消す側の全行を写す必要があるが、FROM / TO なら両端の 1 行ずつで済む。出力の `edits[0] replaced lines 151-158 (8 lines) with 12 lines` で、意図した範囲だけを消したか確かめられるのも良い。
- テンプレートリテラル（`${…}` とバッククォートの入れ子）を含む JS も、`<<'EOF'`（引用符つき）のヒアドキュメントの中でそのまま書けた（場面 4）。python の `'''` で書いていたときの、`\` と `{` の二重のエスケープの心配がない。
- 全部か無しかが効いた（場面 9）。3 つのうち 1 つが外れても、前の 2 つだけが書かれた中途半端な状態にならないので、直して同じ入力を流し直すだけで済む。

## 気づいたこと・要望

- **いちばん多い失敗は「行の一部だけを OLD に書く」**（場面 2・9 の 2 回。どちらも長い 1 行の先頭だけを書いた）。診断が良いので 1 回で直せるが、同じ人（エージェント）が同じ日に 2 回やっているので、書き方の癖として起きやすい。
- **長い 1 行の段落の前後に行を足す型がやりにくい**（場面 2・7・9）。Markdown の文書は 1 段落が 1 行で数百文字になることが多く、区切り形式で行全体を OLD に写すのは長くて写し間違えやすい。今回は JSON で行の先頭の一部を `old` にして、`new` に「足す行 + \n + 元の先頭」を書いた。JSON だと改行が `\n`、引用符がエスケープになり、区切り形式の「そのまま書ける」利点が消える。
  - 案: 区切り形式で、行の一部での照合を明示的に許すマーカー（例: `<<<<<<< OLD partial`）、または「この行の前に挿入」「この行の後に挿入」の形（`<<<<<<< BEFORE` / `<<<<<<< AFTER` に、行の一部を書く）。挿入は既存の行を書き換えないので、行の一部の一致でも安全側だと思う。
- **挿入・追記の型が多い**。9 回のうち 4 回（場面 2・6・7 の 2 か所）は「既存の行は変えずに、前か後ろに足す」だった。区切り形式では、足す場所の行を OLD と NEW の両方に書く（同じ行を 2 回写す）。上の `BEFORE` / `AFTER` があれば、OLD に場所の行を 1 回書くだけで済む。
- ファイルの末尾に追記するだけの場面（記録の文書への追記）は、rpatch ではなく `cat >> file <<'EOF'` を使った。照合が要らないので、rpatch でやる理由がない。
- ヒアドキュメントを `<<EOF`（引用符なし）で書くと、バッククォートと `$` をシェルが展開するので `\`` と `\$` のエスケープが要る（場面 8 で、本文に変数を入れたくて引用符なしにした）。ヘルプの例はすべて `<<'EOF'` なので正しいが、「必ず引用符つきの `<<'EOF'` で書く」と一言あると、エージェントが外さない。
- 未知のオプション（`rpatch -F`、`sd -F` の癖で打った）は終了コード 2 で止まり、何もしない。安全。ただし、ヘルプ全文（約 50 行）が stderr に出るので、1 行の usage と `--help` の案内だけのほうが、エージェントの文脈を食わない。
- 失敗したとき、後ろに `&&` でつないだコマンドは止まるが、改行で続けたコマンドは走る（終了コード 1 は返っている。rpatch の問題ではなく、使う側の書き方の問題）。今回は git commit が先に走った。エージェントに使わせるときの注意として、ヘルプかドキュメントに「続けて実行するコマンドは `&&` でつなぐ」と一言あってもいい。
- Claude Code の Edit ツールと混ぜると、rpatch で書き換えたファイルは「ディスク上で変わった」扱いになり、Edit の前に読み直しが要る（ハーネス側の挙動で、rpatch の問題ではない）。1 つのファイルにはどちらか片方を使うほうが手間が少ない。
