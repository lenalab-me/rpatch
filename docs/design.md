# rpatch の設計

rpatch は、既存の UTF-8 ファイルを完全一致でまとめて編集する CLI。エージェントが Bash から呼ぶことを前提にしている。方針は 4 つ。

- 一致は完全一致だけ。空白や改行の違いを曖昧に許さない。
- 全部か無しか。1 つでも当たらない編集があれば、どのファイルにも書き込まない。
- 失敗したときは、行番号と原因を示して、次の 1 回で直せるようにする。
- 入力はエスケープなしで書ける（区切り形式）。

使い方は `rpatch --help`。MCP サーバーは [mcp.md](mcp.md)。英語版は [design.en.md](design.en.md)、LLM 向けの短い入口は [llms.txt](../llms.txt)。

## 処理の流れ

`lib.rs` の `apply()` が、CLI と MCP の両方から呼ばれる。1 回の呼び出しは次の順に進む。

1. **解析**（`input.rs`、`block.rs`）
   - 先頭の BOM は外す（Windows の PowerShell がパイプに付けることがある）。そのうえで先頭（空白を除く）が `{` なら JSON、それ以外は区切り形式として読む。
   - 区切り形式では、CLI の引数のファイル（`rpatch FILE`）が、最初の `=== <file>` 行より前のブロックの対象になる。エージェントが `rpatch FILE <<'EOF'` と書いて失敗することが多かったため。ファイルは 1 つまで。JSON の入力には使えない。最初のブロックより前に別のファイルの `=== ` 行が来て、引数のファイルが使われないときは入力の誤りにする（黙って無視しない）。
   - `=== ` を付け忘れたパスだけの行（`main.go`）や、diff 風の `--- main.go` も、すぐ次の行がブロックの開始行なら `=== main.go` として読む。意味はひとつにしか取れず、ファイルがなければ file not found になるので、受け付けても壊すことはない。ヒントを出して止めると、エージェントは rpatch に戻らず別の手段に移る。そうした手段は確かめずに書き込むので、止めるほうが危ない。
   - 閉じの行に、開きの行と同じ `part` や `count=N` を書いたもの（`<<<<<<< OLD part` に対する `>>>>>>> NEW part`）も、閉じとして読む。長い区切り（`>>>>>>>>> NEW part`）でも同じ。開きに合わせて閉じを書く誤りで、意味はひとつにしか取れない。前は書式の誤りとして止めていたので、通っていた入力の読み方は変わらない。開きと食い違う語（`<<<<<<< OLD` に対する `>>>>>>> NEW count=2` や `NEW part`、count を取らない `<<<<<<< FROM` に対する count）は、開きと閉じのどちらに従うかで当てる箇所が変わり 2 通りに読めるので、受け付けずに、直した開きの行をヒントに出す。NEW の後ろのそれ以外の語は、今までどおり閉じとは読まない（Git の衝突の印の `>>>>>>> main` のような行は本文にありうる）。閉じの代わりに書いた `=======` も、Markdown の見出しの下線として本文にありうるので受け付けない。
   - 続けて並んだ `=== ` 行（間に空行だけ）は 1 つの組になり、後ろのブロックをそれぞれのファイルに当てる。照合はファイルごとに完全一致で、全部か無しか。ブロックのない `=== ` 行にはほかの意味がないため。最後のファイルにだけ当てると、前のファイルは終了コード 0 のまま黙って変わらない。組の中で同じファイルを 2 度挙げたとき（同じ名前を 2 回、`a.txt` と `./a.txt`、symlink とリンク先）は、ブロックをそのファイルに 1 回だけ当て、出力の行の下に注記を出す。2 回当てると、AFTER が黙って 2 回挿入するため。
   - ファイル名の `~/` はホームとして読む（区切り形式でも JSON でも）。heredoc や JSON の中ではシェルが展開しないため。
   - どちらも `Edit` の列にしてから、まとめて検査する（`input::validate`）。空の OLD、`old == new`、空の BEFORE/AFTER、空の挿入、`count=0` は入力の誤り（終了コード 2）。
2. **読み込み**（`lib.rs` の `load_files`）
   - 編集に出てくるファイルを 1 回ずつ読む。パスは `cwd` を基準に `canonicalize` し、書き方の違う同じファイル（`a.txt` と `./a.txt`、symlink とリンク先）を 1 つにまとめる。symlink はリンク先を編集する。
   - UTF-8 でなければ読み込みの失敗（終了コード 3）。普通のファイルでないパスも同じ（FIFO は、読むと書き手を待ち続ける）。先頭の BOM は外して覚えておき、照合には使わない。
   - 権限とハードリンクの数も覚えておく。
3. **照合と適用**（`matcher.rs`、`lib.rs` の `apply_edits`）
   - 編集を入力の順に、そのファイルの「いまの内容」に当てる。同じファイルへの後の編集は、前の編集の結果を見る。
   - 当たらなかったら、そのファイルの残りの編集は照合しない（「not checked」と表示）。ほかのファイルの編集は照合を続ける。
   - 当たらなかった編集が、同じ一括の前の編集を当てる前の内容なら当たる場合は、そのことも示す（前の編集が文字列を変えてしまった、というよくある間違い）。
4. **書き込み**（`write.rs`）
   - 当たらなかった編集が 1 つでもあれば、何も書かずに終わる。`--dry-run` でも書かない。
   - 先に、書き換えるファイルに読み取り専用のものがないかを確かめる（rename だと読み取り専用でも書けてしまうため）。`--dry-run` でも確かめ、読み取り専用のファイルについて、本番で失敗するものを成功と言わない。ディレクトリへの書き込みは試さないので、書き込めないディレクトリは dry run を通り、本番で失敗する（書き終えたファイルは下のとおり元に戻す）。
   - 同じく、読み込んだあとにファイルが変わっていないか（BOM を含めてバイト単位で同じか）を確かめ、変わっていたら何も書かない（終了コード 3）。ほかのエージェントやフォーマッタ、エディタが同じ作業ツリーで書いた変更を、黙って消さないため。rename の直前にもファイルごとに確かめ直し、すき間を狭める。
   - ファイルごとに、同じディレクトリの一時ファイル（`.rpatch-*`）に書き、`fsync` し、元の権限を付けてから rename で置き換える。BOM があったファイルには付け直す。
   - 途中のファイルで書き込みに失敗したら、それまでに書いたファイルを元の内容に戻す。戻すのにも失敗したら、変更が残ったファイルを報告する。
5. **出力**
   - ファイルごとに `M <file>  edits=<n>  at_lines=<変わった行>` を出す。範囲置換は置き換えた行の範囲を、ハードリンクのあるファイルは警告を、その下に出す。
   - 編集が打ち消し合って内容が元と同じファイルは、`= <file>  edits=<n>  unchanged` と出して書かない（`M` と at_lines では、ない変更を言ってしまう）。
   - `--diff` なら unified diff を付ける。見出しは `a/<file>` と `b/<file>`。絶対パスはそのまま出す。

rename で置き換えるので、ハードリンクは切れる（ほかのリンクは古い内容のまま）。そのときは警告を出す。書き込みに失敗して元に戻したファイルも、同じく rename で戻すので、ハードリンクは切れる。引き継ぐのは権限のビットだけで、持ち主（新しいファイルは rpatch を動かした利用者のものになる）、拡張属性、ACL は引き継がない。読み込んだあとの変更は上のとおり見つけて止めるが、確かめてから rename するまでのごく短い間の変更や、プロセスが途中で止まった場合の巻き戻しは扱わない（ロックは取らない）。

## モジュール

| ファイル | 役割 |
|---|---|
| `main.rs` | 引数の処理、stdin の読み込み、終了コード。`rpatch mcp` を MCP サーバーへ回す |
| `lib.rs` | `apply()`。読み込み、編集の適用、`at_lines` の計算、出力の組み立て |
| `input.rs` | 入力の判別、JSON の解析、`Edit` と `Target` の定義、入力の検査 |
| `block.rs` | 区切り形式の解析と、区切りの書き間違いの診断 |
| `matcher.rs` | 1 つの編集がファイルのどこに当たるかを探す。当たらないときの診断の入口 |
| `diagnose.rs` | 見つからない・数が合わないときの説明（似ている行など） |
| `write.rs` | 全部か無しかの書き込みと、失敗したときの巻き戻し |
| `text.rs` | 行番号の計算と、診断での行の表示 |
| `mcp.rs` | MCP サーバー（Cargo feature `mcp` のときだけ） |
| `help.txt` | `--help` の本文。要約（終了コードの段落まで）と、そのあとの節 |
| `help.rs` | `--help` の出力。要約は 40 行以内で、短く切られても使えるよう、2 行目に詳細の引き方、20 行目までに書き方と注意を置く。`--help TOPIC` で節、`--help all` で全文 |

## 編集の種類

`Edit` は、対象（`Target`）、置き換える文字列（`new`）、一致すべき回数（`count`）を持つ。区切り形式から作った編集は `lines = true`、そのうち `OLD part` は `part = true` も立つ。

| 書き方 | `Target` | 照合 |
|---|---|---|
| `<<<<<<< OLD` | `Text` | 行の先頭からだけ。行全体 |
| `<<<<<<< OLD part` | `Text`（`part`） | どこでも。最後の改行は含めない |
| `<<<<<<< FROM` / `TO` | `Range` | 行の先頭からだけ。最後の行は行の先頭部分でよい |
| `<<<<<<< BEFORE` / `AFTER` | `Insert` | どこでも（1 行以上の一部）。行の境目に挿入する |
| JSON の `old` | `Text` | どこでも |
| JSON の `from` / `to` | `Range` | どこでも |

### 共通の規則

- 一致は重なり合うものも数える（`x\nx\nx` に `x\nx` は 2 回）。重なっていたら `count` に関係なく失敗にする。重なりを数えないと、曖昧な文字列が黙って最初の一致に当たってしまう。
- 一致の数は `count`（既定 1）とちょうど同じでなければ失敗。

### 区切り形式の改行

- ブロックの各行は改行で終わるものとして扱う。ファイルが CRLF なら、ブロックの改行も CRLF に合わせてから照合する。JSON の文字列は変換しない。
- LF と CRLF が混ざったファイルは、区切り形式では編集できないので、専用のエラーにする（どの行が LF で、どの行が CRLF か示す）。合わせる改行が決まらず、LF の行には当たらず、挿入した行は CRLF になってしまうため。JSON なら書いたとおりに照合する。
- ファイルの最終行に改行がないとき、OLD はその行に改行なしで一致させ、置き換えたあともファイルの末尾に改行を足さない（`last_line_match`）。AFTER で最終行の後ろに挿入するときも同じ。

### OLD と OLD part

- OLD は行全体だけに一致する。長い行の先頭だけを書いたつもりで部分一致させると、行の残りが黙って残るので、行の一部としてだけ見つかったときは失敗にして、その行を示す。
- 行の一部を書き換えたいときは `OLD part` と明示する。中身はどこにでも一致し、最後の改行は含めない（JSON の `old` と同じ）。

### FROM / TO

- FROM はちょうど 1 回一致しなければならない。TO は FROM の最後の行より後ろで、最初に一致したもの。
- FROM から TO の手前までを NEW で置き換え、TO は残す。NEW の最後の行が TO の行と同じなら失敗にする（TO が 2 回並ぶ、よくある間違い）。行単位で比べるので、TO が `}` で NEW の最後が `    }` なら通る。
- JSON の `from`/`to` では、`new` の末尾が `to` と同じでも止めない。JSON の文字列は行の一部どうしで、`to` が `)` のような数文字だと、正しい編集でも `new` の末尾に来る（`call(` から `)` の手前までを `call(f(a)` にして `call(f(a))`）。書き間違いと見分ける手がかりが無い。「`new` の末尾＋`to`」が元のファイルにある並びかで見分ける案も、典型的な書き間違い（`{ x }` を `{ z }` にして `{ z }}`）で `}}` が元に無いので見分けられない。行単位で比べられる区切り形式だけで止める。
- TO の行がなければ、FROM からファイルの最後までを置き換える。ファイルの末尾を消すのに、エージェントが `head -n` で行番号を使って切るため。
- FROM・TO・アンカーの最後の行が空行なら、行の先頭部分ではなく空行そのものに一致する。空の先頭部分はどの行にも一致してしまい、TO が空行 1 行だと「ファイルの最後まで」になって後ろの行を黙って消していた。いまは「次の空行まで」と書ける。

### BEFORE / AFTER

- アンカーは 1 行以上（の一部）で、ちょうど `count` 回一致しなければならない。同じ行で 2 回一致したら失敗。BEFORE は一致の始まる行の前に、AFTER は一致の終わる行の後ろに挿入する。アンカーは 2 行以上でもよい。
- 既存の行は書き換えず、アンカーを含む行の前後の境目に NEW の行を挿入する。同じアンカーへの AFTER を重ねると、後の AFTER ほどアンカーの直後に入るので、順番が逆になる。

## 診断

当たらなかった編集には、見出しと説明を付ける。

- **見つからない**
  - 区切り形式で、行の一部としてだけ見つかるなら、どの行のどこ（先頭だけ・末尾だけ・途中）かを示し、`OLD part` や BEFORE/AFTER を案内する（`matcher.rs` の `partial_line`）。OLD なら、同じ OLD と NEW のまま `OLD part` にしたときに行がどうなるかも示す（`part_preview`）。切れた行だけでなく、置き換えたあとの行を 8 行まで並べる。切れた行の前に行を足す編集では、切れた行だけだと元と同じに見えるため。この失敗の多くは長い行の先頭だけを書いたもので、名前を挙げるだけだと、NEW に行全体を書いたときに `OLD part` へ移って行の残りを二重にしかねないため、結果を見せて選ばせる。
  - それ以外は、次の順で最初に当てはまったものを 1 つ出す（`diagnose::not_found`）: CRLF の違い → 空白の違い（該当行）→ どこまで一致してどこで食い違うか → 一番似ている行。
- **数が合わない**: 一致した行の一覧（10 か所まで）と、`count` の書き方のヒント。
- **重なり**: 重なった範囲（同じ行の中なら列）と、前後を足すヒント。
- **入力の誤り**: JSON の構文エラーは該当箇所の前後とキャレット、`\'` や生の改行についてのヒント。区切り形式は、区切りの長さの違いや閉じ忘れのヒント（閉じの代わりの `=======` が入力の最後か閉じの直前にあれば、そう示す）、開きと食い違う閉じの行には直した開きの行、自己流の形式（`--- old` など）には正しい書き方の例。

行の表示は 200 文字で切る。ただし「行の一部としてだけ見つかった」ときの行は、そのままコピーして使えるよう 4000 文字まで出す。

## at_lines

各ファイルについて、編集で変わったバイト範囲（`changes`）を覚えておく。後の編集で内容がずれたら、範囲も付け替える（`splice`）。

- 置き換えた文字列と新しい文字列で、先頭と末尾が同じ行は数えない（文脈として書いた行）。
- 削除は、消えた位置にいまある行を示す。ファイルの末尾を消したときは最終行。
- 範囲は行番号に直して並べ、隣り合うものをまとめる（`3,10-12`）。

## 終了コード

| コード | 意味 |
|---|---|
| 0 | すべて当たった（`--dry-run` を含む） |
| 1 | 当たらない編集があった、ファイルがない、または LF と CRLF が混ざったファイル |
| 2 | 入力の誤り（解析できない、空の OLD、`old == new` など）、引数の誤り |
| 3 | 読み書きの失敗（UTF-8 でない、FIFO やディレクトリのように普通のファイルでない、読み取り専用、読み込んだあとにファイルが変わった、一時ファイルや rename の失敗）|

1 と 3 が同時に起きたら 3 にする。書き込んだあとで結果の出力に失敗したときも 3（読み手が先に終わった `| head` は失敗にしない）。

## 範囲外にしたもの

- 新しいファイルの作成と、ファイルの削除（`cat > file <<'EOF'` や `rm` で足りる）。
- 正規表現での置換（`sd` などの別の道具を使う）。
- 書き込む前の構文チェック。実際に構文を壊す編集はまれで、エージェント自身の確認ですぐ見つかるので見送った。

## テスト

- `tests/cli.rs`: CLI の結合テスト。編集の種類ごとの成功と失敗、診断の文面、書き込みの性質（権限、symlink、BOM、ハードリンク、読み取り専用）を見る。
- 各モジュールの単体テスト（行番号の計算、重なりを含む一致の列挙など）。
- `tests/mcp.rs`: MCP サーバーの接続と、CLI と同じ出力になること（`--features mcp` のときだけ）。

`cargo fmt --check`、`cargo clippy --all-targets -- -D warnings`、`cargo test` を、feature なしと `--features mcp` の両方で通す。CI（`.github/workflows/build.yml`）は手動で起動する。
