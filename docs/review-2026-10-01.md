## 1. 失敗時の出力: とても良い

全部のケースで、次の 1 回で直せる情報が出ていた。

- インデント違いのとき、該当する行の範囲を出し、「あいまいな一致はしない」と明言している。Codex の apply_patch は黙ってインデントを崩していたので、ここが一番の価値。
- 「複数行の途中で食い違う」のとき、`old` の行とファイルの行を並べて見せてくれる。
- マッチが重複したときに全部の行番号と `count` のヒントを出す。CRLF を指摘する。cwd を表示する。
- **複数の失敗を一度に報告する。** 1 つずつ直すと、往復の回数がそのまま増えてしまう。
- アトミックである、実行権限を保持する、シンボリックリンクの先を編集してリンク自体は残す、の 3 点も確認できた。

## 2. JSON のエスケープ: 一番の課題

- 1 行で短い置換なら、JSON でも負担はない。
- **複数行のブロックはつらい。** 20 行のコードが `\n` でつながった 1 行になり、読めなくなる。JS や HTML はもともと `"` が多い。正規表現は 2 重にエスケープが必要になる（`\\\\n`）。
- **ログでの裏付け**: 9 月以降の python での置換 342 回のうち、**195 回は `'''` の複数行文字列を使っていた**。置換の過半数にこの負担がかかる。
- **間違えやすい例**: JS の `'it\'s'` をそのまま貼ると、JSON では不正なエスケープになる。生の改行も同じく不正になる。どちらも終了コード 2 になるが、出力は `invalid escape at line 1 column 57` だけ。
  - → 該当箇所の前後の文字列と、ヒントを出してほしい（「JSON では `\'` は不正です。`'` はそのまま書けます」「改行は `\n` で書きます」など）。

### 形式の提案

aider の SEARCH/REPLACE に近い形にする。モデルが学習データで見慣れている可能性が高い。

```
rpatch <<'EOF'
=== app.mjs
<<<<<<< OLD
function help(svc, cmd) {
  const key = `${svc} ${cmd}`;
=======
function help(svc, cmd, sub) {
  const key = sub ? `${svc} ${cmd} ${sub}` : `${svc} ${cmd}`;
>>>>>>> NEW
EOF
```

- ブロックの中身はそのまま書き、エスケープはしない。
- `count` はヘッダー行で指定する（`=== app.mjs count=2`）。
- 決めておく必要があるのは、ブロックの最後の改行を含めるかどうか。行単位で扱うのがおすすめ。
- JSON 形式も残す。短い置換には JSON、ブロックの置換には区切り形式、という分け方にする。

## 3. python の置換との比較

- **安心感は rpatch が明らかに上。** マッチ数の厳密な確認、アトミック、編集後の行番号の表示がある。python だと assert を毎回書く必要があり、書き忘れると黙って空振りしていた（86 回）。
- **手間**: 1 行の置換なら同じくらいか、ヘルパーを書かなくていいぶん rpatch のほうが楽。複数行のブロックだと、今は python の `'''` のほうが楽。区切り形式ができれば逆転する。

### 足りない機能（9 月以降の python での置換 342 回を数え直した結果）

| python での書き方 | 回数 | rpatch での扱い |
|---|---|---|
| `s[s.index(A):s.index(B)]` で範囲を切り出して置換 | 70 | **アンカー間の範囲置換を追加（優先度高）** |
| アンカーの直後に追加 | 41 | `old` = アンカー、`new` = アンカー＋追加分で、今でも書ける |
| JSON を読み込んで構造ごと書き換え | 40 | jq の担当。範囲外 |
| `re.sub` | 6 | 要らない |
| ファイルの作成 | — | `cat >` で足りている。要らない |

アンカー間の範囲置換の案: `{"file": "...", "from": "A", "to": "B", "new": "..."}`。A と B はそれぞれちょうど 1 回マッチしなければ失敗にする。A と B 自体を置換の範囲に含めるかどうかは、決めておく必要がある。大きなブロックを、`old` に全部書き写さずに差し替えるための機能。

## 細かい点

- `old == new` で実際には何も変わらないのに、`M ... edits=1` と表示される。Edit ツールのようにエラーにするか、`unchanged` と表示したほうがいい。
- 同じファイルで先の編集が失敗すると、あとの編集は `not checked` になる。失敗した編集を飛ばして、元の内容に対して照合した結果も出せれば、1 回の往復で全部直せる。必須ではない。

## 優先順位の提案

1. 区切り形式の入力
2. アンカー間の範囲置換
3. JSON エラーのヒント
4. `old == new` の扱い
