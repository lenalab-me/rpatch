# rpatch v0.2.0 の試用レビュー

2026-10-01、`~/project/lab/zatsudan` のセッションで試用した。対象はコミット `6f3ed42` の時点の `target/release/rpatch`（`-V` で 0.2.0）。

## 結論

区切り形式で、複数行の置換について python の `'''` に戻る理由がなくなった。前回の 4 項目はどれも期待どおりに動いた。

直してほしいのは次の 3 つ。どれも、何も書き込まずに止まる安全な失敗で、次の 1 回で直せた。なので、このまま普段の作業で使い始めていいと思う。
- 範囲置換で TO が見つからないときの診断が、FROM の行を指す
- 行の一部だけを書いたとき、「空白違い」と出る（本番で 1 回）
- 本文に区切りの記号を含む文書（rpatch 自身のドキュメントなど）を編集できない（本番で 1 回）

## 試したこと

**成功するはずのケース**: 1 回の呼び出しで次のすべてを行い、1 回で通った。`--diff` の出力も正しかった。
- 2 ファイルに 6 つの編集
- バックスラッシュの入った正規表現（`/^\s*(\d+)\\n"(.*)"$/`）、テンプレートリテラル、`'it\'s "ok"'`、日本語をそのまま書いた
- `count=2`、FROM/TO での削除（NEW を空に）、FROM/TO での置換

その他に試して問題なかったもの:
- CRLF のファイル: 改行が CRLF のまま保たれた
- 最終行に改行がないファイル: 改行がない状態のまま保たれた
- パスに空白があるファイル
- `=== file` のあとの空行、ブロックの間の空行、ヘッダー行の末尾の空白
- OLD の最後の空行（意図的に空行も含めて置換できる）
- JSON での範囲置換（行の途中でも照合する）
- TO が FROM と同じ形のとき（`<section id="a">` から次の `<section` まで）: 正しく次のものを選んだ

**失敗するはずのケース**:
- インデントを省いた
- `>>>>>>> NEW` の書き忘れ
- `=======` の書き忘れ
- `<` が 6 個
- `=== file` がない
- FROM の重複
- TO が見つからない
- TO が FROM の前にしかない
- OLD が空
- 行末に余計な空白がある
- 中身に競合マーカーのような行がある

## 1. 区切り形式: 書きやすい。python の `'''` と同じか、それ以上

- コードをそのまま貼れる。正規表現のバックスラッシュや `\'` を、何も考えずに書けた。前回の JSON では、ここが一番自信のないところだった。
- 1 ファイルに複数のブロックを書けて、ブロックごとに `count` を指定できる形は、実際に書いてみると自然だった。ヘッダー行に `count` を書く前回の提案より良い。
- Bash の呼び出しとして見ても、編集前と編集後が上下に並ぶので、許可を求める画面でユーザーが読みやすい。python スクリプトより一目で分かる。
- 区切りを書き間違えたときのエラーは、全部 1 行で何が起きたか分かった（`line 5: unexpected >>>>>>> NEW inside the OLD block that starts at line 2` など）。
  - 改善するなら、「書き忘れていそうなもの」を 1 行ヒントとして足すとさらに早く直せる。たとえば `>>>>>>> NEW` の書き忘れなら `hint: missing >>>>>>> NEW before line 6?`。
  - 細かい点: このケースでは「the NEW block that starts at line 2」と表示されるが、line 2 は OLD の開始行。NEW は line 4 の `=======` から始まる。

## 2. 行の先頭からに限る照合: 不便ではない。むしろ安心できる

- インデントを省いたときに「行の途中にはある」と、その行番号まで出してくれる。ヒントが `copy the whole lines, including leading whitespace` なので、次の 1 回で直せる。
- 行単位で考えるのは、python の `'''` で書いていたときの感覚と同じ。行の途中を置き換えたいときは JSON がある、という分け方も分かりやすい。
- 行末に余計な空白がある場合も、「空白違いで 11 行目に一致」と出て、すぐ分かった。

### 本番で 1 回失敗した: 行の一部だけを書いたときの診断が分かりにくい

メモリファイルの更新で、python で `s.index('**Why:**')` と書いていたときの癖のまま、FROM に `**Why:**` とだけ書いた。実際の行は `**Why:** 仕様は「速さ」ではなく…` だった。出力は次のとおり。
```
error: edits[0] agent-edit-tool-idea.md (input line 2): "from" not found
  found with different whitespace (indentation, spacing or line breaks) at line 30:
      30 | **Why:** 仕様は「速さ」ではなく、…
  hint: copy "old" exactly from the file; rpatch never matches loosely
```
- 行番号が出ていたので、次の 1 回で直せた。ただ、原因は空白の違いではなく、**行の一部しか書いていないこと**。
- 期待する出力: `found as part of line 30 (the block format matches whole lines): copy the whole line, or use JSON to match part of a line`。
- ヒントのラベルも、FROM なのに `"old"` になっている。
- 範囲置換のアンカーは、行の一部（`**Why:**` や `## 見出し`）で書きたくなりやすい。なので、この診断はよく出番があると思う。

### 本番でもう 1 回失敗した: rpatch の書き方を含む文書を rpatch で編集できない

この review.md に上の節を追記しようとしたら、本文に書いた例の `<<<<<<< FROM` が区切りとして解釈された。
```
rpatch: line 11: unexpected `<<<<<<< FROM` inside the NEW block that starts at line 2
```
- 長い Markdown を JSON で書くのはつらいので、結局 Edit ツールで追記した。
- ログには競合マーカーの例が 0 回だったので、急がない、と上に書いた。ただ、**rpatch 自身のドキュメント（README、--help の説明、レビュー）を編集するときは毎回これが起きる。** 試用の初日に起きたので、改善案 3（記号の数で入れ子にできるようにする）の優先度を上げたほうがいい。

## 3. 範囲置換: 直感に合う。ただし TO が見つからないときの診断にバグがある

- 「FROM は置き換え、TO は残す」は、python の `s[:a] + new + s[b:]` と同じで直感に合う。
- `edits[3] replaced lines 18-21 (4 lines) with 0 lines` の表示で、範囲が意図どおりか確認できた。この表示は必ず出してほしい。
- **気をつける点（仕様どおりの動き）**: `// --- debug` から `// --- end debug` までを削除すると、終わりの印（TO）が残る。印ごと消したいときは、TO に次の行を指定する必要がある。表示ですぐ気づけたので、今のままでいい。`--help` に「TO は残るので、印ごと消すなら次の行を TO にする」と 1 行あるとなおいい。

### バグ: TO が見つからないときの診断が、TO ではなく FROM の行を指す

```
=== index.html
<<<<<<< FROM
  <section id="a">
<<<<<<< TO
  <section id="c">      ← 実際にあるのは 8 行目の <section id="b">
```
出力:
```
error: edits[0] index.html (input line 2): "to" not found after "from" (line 4)
  "old" matches the file up to a point, then differs at line 4:
     old |   <section id="c">
       4 |   <section id="a">
  (the matching part occurs 2 times; showing the first)
```
- ラベルが `"to"` ではなく `"old"` になっている。
- 似た箇所を **FROM より後ろだけ** から探しておらず、FROM の行そのもの（4 行目）を出している。本当に見せたいのは 8 行目の `<section id="b">`。
- 期待する出力: `"to" not found after "from" (line 4); most similar after it: line 8 |   <section id="b">`。

「TO が FROM の前にしかない」場合（`"to" occurs only before "from", at line 4`）の診断は正しく、分かりやすかった。

## 4. まだ python に戻りたくなる場面

9 月以降の python での置換 342 回を数え直した結果と、今回試した結果から。

| 場面 | 回数 | 意見 |
|---|---|---|
| 行ごとの変換（再インデント、`"\n".join(...)` など、計算で中身を作る置換） | 22 | python のまま。rpatch の範囲外でいい |
| 同じ置換を複数ファイルにループで当てる | 3 | 少ないので不要。`=== file` を並べれば書ける |
| 中身に `<<<<<<< ` / `>>>>>>> ` で始まる行がある（競合マーカーなど） | 0 | 今は JSON で書くしかない。下の改善案を参照 |
| 中身に `=======` だけの行がある | 0 | 実際には出てきていない。今の仕様でいい |

それ以外の置換（全体の 9 割以上）は、rpatch の区切り形式で書けると思う。

## 改善案（優先順）

1. **（バグ）** TO が見つからないときの診断を、FROM より後ろだけから探して、ラベルを `"to"` にする。
2. **（バグ）** 行の一部だけを書いたときに「空白違い」と出るのを、「行の一部として見つかった（区切り形式は行全体で照合する）」に直す。ヒントのラベルも、`old` / `from` / `to` を正しく出し分ける。
3. **記号の数で入れ子にできるようにする**（本番で起きたので優先度を上げた）。Markdown のコードフェンスと同じ考え方で、たとえば `<<<<<<<<< OLD`（9 個）で開いたブロックは、9 個の `=========` と `>>>>>>>>> NEW` で閉じる。中にある 7 個の行は中身として扱う。それまでの間は、エラーに `hint: use JSON, or longer markers` のようなヒントを足す。
4. 区切りの書き間違いに、「書き忘れていそうなもの」のヒントを足す。あわせて、NEW の開始行の表示を直す。
5. `--help` に、範囲置換で終わりの印ごと消すときの書き方を 1 行足す。
